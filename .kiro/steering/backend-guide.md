# 백엔드 개발 가이드 — 아무거나 말고

## 1. 프로젝트 기본 정보

- **서비스명**: 아무거나 말고
- **마스코트**: 아무고릴라
- **개발 환경**: 5시간 해커톤, 2인 병렬 개발
- **프론트엔드 담당**: 주영 / **백엔드 담당**: 혜린
- **이 파일의 작업 범위**: `backend/` 및 `.kiro/steering/backend-guide.md`

---

## 2. 기술 스택

| 항목 | 내용 |
|---|---|
| 언어 / 프레임워크 | Python 3.11 + FastAPI |
| 데이터 저장 | 백엔드 메모리 (DB 없음) |
| 인증 | 없음 (로그인 불필요) |
| 외부 API / AI | 사용하지 않음 |
| 프론트엔드 폴링 주기 | 2초마다 GET 요청 |
| CORS 허용 출처 | `http://localhost:5173` |
| JSON 필드명 규칙 | snake_case |

---

## 3. API 개발 규칙

- 승인된 `design.md`의 API 6개를 **정확히** 구현한다.
- API 경로, HTTP Method, 요청·응답 JSON 필드명을 **임의로 변경하지 않는다**.
- 명세에 없는 필드나 기능을 **추가하지 않는다**.
- 프론트엔드와 백엔드의 API 계약을 최우선으로 한다.
- Spec이 아직 없거나 승인되지 않았다면 구체적인 API 구조를 **추측하지 않는다**.

---

## 4. 방 및 사용자 관리

- 방 상태는 `collecting → voting → done` 순서로 전환한다.
- 단계 전환 조건은 승인된 Spec을 따른다.
- `member_id`는 UUID를 사용한다.
- 방 정보에 `host_id`를 저장한다.
- 방장 전용 요청은 `member_id == host_id`인 경우에만 허용한다.
- 로그인 없이 방 코드와 닉네임으로 참여한다.
- 후보 중복 제출 및 중복 투표를 방지한다.

---

## 5. 후보 중복 통합 규칙

통합은 **투표 시작 시점**에 수행한다.

1. 후보 이름의 앞뒤와 중간 공백을 모두 제거한다.
2. 영문은 소문자로 변환한다.
3. 정규화된 이름이 완전히 같으면 하나의 후보로 통합한다.
4. 통합 후보의 표기는 **가장 먼저 제출된 표기**를 유지한다.
5. 모든 어필멘트는 등록 순서대로 보존한다.
6. 어필멘트와 함께 추천인의 신원을 **공개하지 않는다**.

---

## 6. 결과 결정 규칙

아래 순서를 **정확하게** 따른다.

1. 거부권을 받은 후보를 제외한다.
2. 남은 후보 중 좋아요가 많은 순으로 정렬한다.
3. 좋아요가 같다면 싫어요가 적은 순으로 정렬한다.
4. 그래도 1등이 동점이면 동점 후보와 어필멘트를 공개한 뒤 **랜덤**으로 최종 1등을 결정한다.
5. 모든 후보가 거부권을 받았다면, 거부권을 가장 적게 받은 후보들 중에서 2~4번 규칙을 적용한다.

### 결과 JSON 필드 규칙

| 필드 | 규칙 |
|---|---|
| `tied_candidates` | 동점 없으면 빈 배열 `[]`, 동점이면 동점 후보 목록 (추천인 정보 제외) |
| `tie_break` | 동점 없으면 `null`, 동점이면 `"random"` |
| `winner`, `winner_added_by`, `winner_appeals`, `ranking` | 승인된 기획서 및 Spec을 따름 |
| 추천인 공개 | 최종 1등에게만 공개 |

---

## 7. 상태별 데이터 공개 규칙

| 방 상태 | 공개 범위 |
|---|---|
| `collecting` | `candidates`를 빈 배열 `[]`로 반환 |
| `voting` | 후보 목록 반환, 추천인 정보는 비공개 |
| `done` | 승인된 결과 JSON 형식을 그대로 반환 |

---

## 8. 코드 작성 원칙

- 모든 백엔드 코드는 `backend/` 폴더 내부에 작성한다.
- **프론트엔드 파일을 수정하지 않는다.**
- 단순하고 읽기 쉬운 코드 구조를 유지한다.
- 5시간 해커톤에 맞춰 **MVP 완성을 최우선**으로 한다.
- 불필요한 패키지, 추상화, 복잡한 아키텍처를 도입하지 않는다.
- API의 오류 처리와 유효성 검증을 구현한다.
- 기존 코드와 충돌이 발생하면 **임의로 덮어쓰지 않고 먼저 알린다**.

---

## 9. Spec과의 관계

- 주영이 별도 컴퓨터에서 `requirements.md → design.md → tasks.md`를 작성 중이다.
- 각 Spec 문서는 단계별 검토와 승인 후 확정된다.
- 이 Steering 파일은 개발 원칙을 정의하며, **Spec을 대체하지 않는다**.
- 승인된 Spec과 Steering이 충돌하면 **임의로 판단하지 말고 충돌 내용을 보고한다**.
- 승인된 Spec의 API 계약, 숫자, 상태 전환 조건을 임의로 변경하지 않는다.
